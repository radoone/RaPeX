# Resumable merchant monitoring

The 3 November 2026 production trace showed 449 Safety Gate records taking about 8 minutes 46 seconds to prepare a merchant shortlist, before AI work began. Each source's GTIN, text-vector and picture-vector searches were awaited serially. Completed matcher chunks were cached, but a task retry rebuilt the database shortlist and replayed completed product writes.

Monitoring now prepares four independent source searches at a time, merges results in the original source order and retains only one four-source result window. Per-source GTIN priority, all eligible text/picture candidates, distance thresholds and image priority are unchanged. AI still handles at most two products concurrently, with the existing bounded 12-candidate matcher batches. A failed product window drains its sibling before the run lease is released.

For calls with a durable run ID (daily/queued monitoring and initial-catalog monitoring pages), a prepared page is published below that run after all of its source and product snapshots have been persisted. It contains official source facts once, allowlisted product facts and references to candidate sources including picture order. It never stores search vectors or OAuth credentials. Retry loads the same source/checkpoint snapshot, restores progress and processes only products without a completion marker. No further source retrieval is needed after publication. An interruption during preparation itself recomputes preparation; no partial page is presented as complete. Calls without a run ID receive the bounded retrieval improvement but do not gain cross-request resume identity.

The private collection groups are `monitoring_work_heads`, `monitoring_work_pages`, `monitoring_work_sources` and `monitoring_work_products`. Each work record carries `expireAt` seven days after preparation. The dedicated storage configuration script enables TTL and disables unused single-field indexes only for these groups. TTL deletion is asynchronous; completed run summaries, checks, findings and merchant decisions retain their existing retention rules. GDPR tenant deletion still recursively removes these nested documents. Missing or oversized prepared inputs fail closed rather than skipping coverage.

A product completion marker is written only after the current-version check and finding writes finish. Products deleted or superseded after preparation cannot produce stale checks/findings. Findings created by a durable product work item carry its private `monitoringWorkKey`; a retry can count its own earlier successful creation without creating another finding or changing a merchant decision. Unrelated existing findings still count as pre-existing. Source and change-journal cursors advance only after every product work item in the page finishes.

Release with `firebase/functions/scripts/scoped-monitoring-work-release.py`: prepare, validate, deploy, check. It snapshots each of the three consumers' deployed source and lock, overlays `monitoring-work.ts`, replaces only the monitoring function and patches finding accounting without replacing other lifecycle code. It preserves each consumer's existing product-version predicate. Runtime settings, secret bindings, triggers, matcher models and prompts remain unchanged. Configure work TTL/indexes with `scripts/configure-monitoring-work-storage.py`; do not redeploy unrelated index definitions or the whole backend. Private rollback and live evidence are under `outputs/monitoring-performance-2026-11-03/`.

All 151 backend tests passed. Coverage includes restoring the original source page after an injected model failure, skipping committed products, preserving candidate image order, restoring finding counts after interruption between finding creation and product completion, draining sibling work, partial preparation, missing inputs and installation deletion/replacement. Live speed measurements and actual worker completion are separate checks; a theoretical four-request bound is not a claim of a fourfold end-to-end speedup.

Read-only live retrieval benchmark on 40 actual Safety Gate records: serial retrieval took 110,150 ms; four-source windows took 34,271 ms (3.21× faster). Both returned the same 212 product/source pairs, source order and matched-image priorities (identical SHA-256 digests). This benchmark made no model calls and wrote no merchant data; it measures retrieval, not end-to-end AI runtime. Evidence: private `retrieval-benchmark.json`.

A production Firestore round-trip also saved a prepared page from existing source/product facts, loaded it through a fresh store instance and preserved its completion marker without vector copies. The isolated `monitoring_work_validation` workspace was recursively removed. It made no model calls and wrote no merchant check, finding or monitoring cursor; this verifies storage/resume transport, not a completed real safety scan (`live-storage-roundtrip.json`). All three scoped function revisions were ACTIVE with preserved configuration. TTL policies were accepted and initially reported CREATING; policy creation is not evidence that documents have already expired.

## Projected searches and page-local product facts

A second 3 November optimization projects merchant GTIN searches to `sourceUpdatedAt` and `deletedAt`, and KNN searches to those fields plus the computed `distance`. Search vectors and repeated descriptions/images no longer travel with every hit. Threshold expansion, exact-code priority and all-picture retrieval remain unchanged. The live Firestore parity benchmark verifies that projected KNN still returns its computed distance.

After each source's searches finish, candidate product facts are hydrated through `getAll` with an explicit field mask, in chunks of at most 100 documents. A single shop/page-local cache shares pending and resolved reads by document ID and source version across the four concurrent source searches. It retains at most 2,048 resolved entries or 16 MiB of estimated JSON facts, evicts resolved entries first, and never shares data between shops, pages or requests. Failed reads propagate and are evicted for retry. Missing, deleted or changed documents cannot be combined with earlier search metadata; final check/finding writes keep their existing authoritative version fences. Source-specific matched-picture priorities stay on independent candidate objects, outside the shared facts.

The 40-source read-only live A/B benchmark used four-source windows on both versions. Both returned exactly the same 212 candidate pairs, allowlisted matcher facts and matched-picture order (identical SHA-256 digest). Baseline: 46,690 ms and 68,179,037 serialized JSON bytes across 1,397 returned search documents. New: 19,231 ms and 149,444 JSON bytes including 58 hydrated documents in 12 batch calls. This run was 2.43× faster with 99.78% fewer returned JSON bytes. These are serialized response sizes, not measured network-wire bytes; sequential A/B timings include normal service/cache variability. Projection does not eliminate billed KNN reads, and hydration adds document reads. No model calls or merchant writes were made. This is a retrieval benchmark, not an end-to-end AI latency or billing claim.

All 159 backend tests pass, including overlapping pending reads, version isolation, tenant/page isolation, deletion/version fences, failed batch retry, bounded retention, projection fields, EAN priority and independent picture ordering. Release this change using `firebase/functions/scripts/scoped-monitoring-products-release.py` (prepare, validate, deploy, check). It snapshots each consumer's deployed source and lockfile, adds only the product-cache module, and patches only the finder, loader factory and monitoring page preparation. Other deployed lifecycle code and runtime settings are preserved. Private benchmark, rollback sources and deployment verification are under `outputs/monitoring-product-cache-2026-11-03/`.
