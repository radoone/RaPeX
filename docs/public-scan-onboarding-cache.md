# Public scan cache and Shopify onboarding

Prepared on 3 November 2026. Deployment must wait until the owner's currently running public-store refreshes finish. Existing refresh workers keep their original compiled scanner; do not rebuild `firebase/functions/lib` underneath them.

The initial catalog importer now asks the authenticated Shopify Admin API for the canonical `myshopifyDomain` and primary-domain host in the same request as the products. The canonical domain must equal the installed shop. Only those returned domains authorize reads of `rapex_leads/{domain}/products/{productId}`. A request-supplied storefront domain never authorizes cross-store cache reuse.

The importer batch-loads compatible public text/image vectors. Text requires the identical embedding input, matching product ID, unexpired retention, a known model/input contract and a finite nonzero 1536-dimensional vector. Images additionally require the identical primary-image URL, multimodalembedding@001 and a valid 1408-dimensional vector. The original unlabelled text cache contract is explicitly frozen to gemini-embedding-001/1536/buildEmbeddingText v1, verified against its introducing commit `ebe0fc2`; a future model change must not reinterpret those legacy rows. Importing vectors does not set `lastCheckedAt` or complete a safety check.

Public scanning now calls the same `retrieveAlertsWithRag` cached-vector path as merchant checks, passing its batched text vectors and cached/bounded primary-image embeddings. This shares validated GTIN recall, 12 text/6 image limits, distance thresholds, image-source hydration and the existing shortlist-only matcher. It never creates a fake merchant or accesses a private merchant installation for public matching. This matches the existing merchant cached-vector behavior, which uses the primary image vector for retrieval; matcher image limits remain unchanged.

After a successful page, public product documents store unfiltered positive **and negative** results under `safetyCoverage`, together with a product fingerprint, matching-policy hash and server read time captured **before retrieval**. The lead/report display threshold does not alter that portable result. Failed retrieval/model work cannot publish completed coverage. Coverage writes use ten-result commits to respect Firestore's 10 MiB request limit. Public product retention remains 90 days; the existing `products.safetyCoverage` index exemption covers these nested facts too.

Onboarding reads portable coverage only from the domains recorded by the authenticated importer. Within a transaction, it verifies product facts/version, policy, expiry, result schema, current merchant installation and absence of later `rapex_changes`. Valid coverage becomes installation-fenced merchant coverage with its original `coveredThrough`; normal audit code still creates merchant checks/findings and preserves merchant decisions.

When storefront JSON omitted GTINs, an otherwise identical identifier-free public result can be supplemented with Admin-only GTIN lookup. Exact GTIN matches are evaluated by the existing deterministic identifier path and take priority over similarity results. The supplemental operation owns a lease and publishes nothing on failure. Removing/changing identifiers from a public result that already used GTIN evidence requires a fresh check.

If source changes have appeared since the public checkpoint, this first implementation conservatively performs the normal current-index merchant check. It does **not** yet replay only that gap during onboarding. After a successful initial audit, existing merchant delta monitoring remains responsible for later source changes. Changed product facts also invalidate coverage while compatible vectors may still be reused.

Older public results lack the shared retrieval contract and complete negative receipts. They cannot be labelled as upgraded without running the new scanner. A later new upgrade run can reuse compatible text vectors and add image retrieval/coverage; it must not resume an old run whose successful pages would be skipped. No automatic upgrade sweep or prospect email is started by this change.

Validation uses an isolated project copy under `/tmp/zr-onboarding-validation`, preserving the compiled modules used by running workers. Tests cover domain fencing, model/dimension/text/expiry validation, negative and positive coverage, policy/source changes, missing Admin-only GTIN supplementation, retirement/deletion, failed supplemental checks and embedding fallback. The release helper snapshots each live function's own source and lockfile, patches only reviewed consumers/helpers, and verifies both local and server-side refresh completion before deployment. Its targets are `merchantCatalogAuditTask`, `scanPublicShopifyStoreAPI`, and `freeScanCatalogTask`. Private snapshots/evidence live under `outputs/onboarding-cache-2026-11-03/`.

All 219 backend tests passed in the isolated project. The final projection/prompt-fingerprint changes also passed 24 focused tests. All three preserved production bundles built and passed their applicable focused tests; their matching-policy/prompt hashes agree. Targeted ESLint and whitespace checks passed. The `watch` command was started in session `42787`; `watch-status.json` currently records `waiting_for_scans`. It waits in 30-second intervals, requires successful completion of the remaining batch (excluding the explicitly deleted shop), independently checks the durable 4kidspoint/batch run states, then runs the guarded deployment and revision/configuration verification. Failures or source/deployment drift stop it. Read the current status/log/verification files before reporting a deployment; arming the watcher is not deployment success.
